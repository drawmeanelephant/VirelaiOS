# M89a (R1) — Declare the PDF subset, choose the engine, and approve hostile-input budgets

- **Parent index:** M89, [#1916](https://github.com/drawmeanelephant/VirelaiOS/issues/1916).
- **Owner:** Sol 6.1, architecture/spec pass; Astra is also authorized by the index. Claude grounds the draft; project owner reviews the decision.
- **Size / scheduling:** 8 agent hours, week one; no renderer implementation.

## Deliverable

Land the complete PDF R1 in one ADR: the exact supported and excluded feature lists, a no-libc/no-POSIX engine survey and reasoned rejection of at least one tempting approach, numeric binary/time/memory/dimension and hostile-input limits, malformed-input behavior, the explicit relationship to M90, and a reviewed disjoint, closable implementation-card split. v1 produces page bitmaps, not a viewer, editor, form engine, generator or print pipeline. Text extraction/search requires explicit R1 justification; encrypted files are outside v1.

## Required design answers

1. Enumerate exact PDF file structures, content operators, fonts/text and image XObjects accepted by v1, and the explicit exclusions. Examples in the index are possibilities, **not** approvals. Define bounded errors for unsupported and malformed inputs, partial output and cleanup.
2. Compare embedding MuPDF, porting a minimal parser, and a from-scratch subset parser against actual dependency surfaces, licensing, weight and maintenance. Reject at least one plausible wrong approach with evidence. The repository is proprietary (`LICENSE`), and ADR 0028 refused to vendor AGPL Elk for that reason (`0028:216-218`). MuPDF is distributed under AGPL-3.0 or a commercial Artifex license, so treat it as license-blocked unless the owner records otherwise. Pin any selected dependency and make builds offline.
3. Approve all numeric budgets below, with units, accounting rules and stated hardware/page workload. Bound decompression, object traversal, recursion and work, not just the final raster allocation.
4. Name what M89 requires from M90's **function-level vector contract**. State precisely what happens if it has not landed: a dependency that blocks the raster card, or an explicitly owned alternative justified by R1. No copying M90 internals or assuming SVG parsing equals PDF rendering. Two constraints bind this answer:
   - A function-level call works only inside one language and one static binary; ADR 0030 D3 forbids cross-language linkage. M90a's language choice therefore fixes M89's engine language, unless M89 consumes a file-format contract instead. Say which.
   - The proposed M89 page cap (1,024 × 1,536) exceeds M90a's proposed SVG canvas cap (1,024 × 1,024). The vector contract must cover M89's page dimensions, or M89 tiles; state which.
5. Finalize the M89b/c shapes, tests, declared corpus, reference-image provenance and comparison rules. A tiny corpus must not silently erase the declared subset. Write every reservation in coordination-gate syntax: exact paths or `dir/*` prefix globs. The gate does not expand `**` (`tools/status/verify-issue-coordination.sh:89-101`).
6. **Language boundary.** A Go engine under `user/go/` needs no ADR change (ADR 0030 D2). Relevant Go prior art: `user/go/ttf/raster.go` is an anti-aliased non-zero-winding coverage rasterizer, and `user/go/draw` provides bounded shape primitives. Any C or Zig native engine is a new program outside ADR 0030 A1's closed four-workload allowlist. It needs an owner-approved ADR 0030 amendment drafted by this R1 (`0030:228-236,366`). Go cannot link such an engine (D3). No new Go FFI, libc, POSIX layer or unauthorized Zig app.

### Proposed numeric budgets, not measured results

R1 may replace these with justified numbers, but its merged output must contain every numeric limit.

| Required budget / hostile-input limit | Draft ceiling |
|---|---:|
| Engine/parser binary bytes added versus equivalent empty adapter | 2,097,152 bytes |
| Per-page rasterization time, 1,024 × 1,448 output pixels | 5,000 ms |
| Peak raster memory per page, including output, scratch and resident document data | 12,582,912 bytes |
| Supported page raster dimensions | 1,024 × 1,536 pixels maximum |
| Input file size | 4,194,304 bytes |
| Parsed object count | 8,192 |
| Object/reference traversal depth | 32 |
| Nested content/graphics traversal depth | 16 |
| Total expanded stream bytes per page | 16,777,216 bytes |
| Work units per page, with unit definition supplied by R1 | 1,000,000 |

Reference hardware: Apple M4, 16 GiB host RAM, macOS 27.2, Apple VZ with 2 vCPUs and 256 MiB guest RAM. The proposed page-time measurement includes parse/decode/raster work, excluding host launch and reading the input transport; measure each corpus page and report the maximum. R1 must define behavior at every boundary, unit conversions from PDF page geometry and document-level resident-data accounting. Expanded bytes are cumulative work, not permission to retain them all at once.

The memory ceiling is tight. A fully resident 4 MiB input plus a maximum-page 32-bpp output (6 MiB) leaves 2 MiB for scratch and decoded images. One full-page RGB image XObject at output resolution (about 4.5 MiB) cannot be held whole, so R1 must stream or downsample it, or change the ceiling. The whole process also shares 4,096 recorded demand pages (about 16 MiB) and 16 mmap regions (`kernel/src/process.zig:124-130`). On a Go route, the runtime grows its heap one mmap region per grow and needs collector headroom inside the same cap. R1 must measure whether a 12 MiB live peak fits; 256 MiB of VM RAM is not a per-process allocation entitlement.
